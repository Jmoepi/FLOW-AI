# Security review: M0 to M2 code

Scope: our own code on branch `feat/m0-m2-scaffold` (scripts, `packages/contracts`, `packages/policy-engine`, `packages/xrpl-adapter`, workspace/config files, git hook). Method: defensive read-through of all code against spec sections 1, 10.4, 13 (13.1A to 13.1C, 13.3), 14.4, 17 and 20, plus the M1 reviewer notes, followed by fixes and tests. Nothing was committed or pushed, no transaction was submitted and no RLUSD was spent. `.secrets/` and `.env` values were not read into this document; only key names are referenced.

Severity scale: Critical (direct loss of funds or key), High (bypass of a core control), Medium (weakens a control or leaks secret-shaped data under plausible conditions), Low (hardening, hygiene). Status: Fixed, Mitigated, Accepted, Open (with owner milestone).

Result: 0 Critical, 1 High (F-01), 7 Medium (F-02 to F-07 and F-19), 13 Low. Every Critical/High/Medium finding in existing code is Fixed. The one Open item, F-19 (Medium), is a future-facing M3 precondition rather than a defect in current behaviour, and is recorded as a binding rule (PG-4). All Lows are Fixed or Accepted with reasons.

## Checks requested in the brief, by area

1. Secrets and key handling. Seeds are read in three places only: `setup-testnet-accounts` (creation), `trust-lines` (signing TrustSet) and `loadSigningWallet` (M1). The seed never appears in an error message, log entry, JSON log or process argument (scripts take no seed arguments; the signer closure `walletSigner` holds only the `Wallet`). Seed values are not in `process.env` unless the owner sets `XRPL_*_SEED` for future guard use; nothing dumps `process.env`. `.secrets/`, `.env*`, `*.seed`, `*wallets*.json`, `*.pem`, `*.key`, `*.p12`, `*.pfx` are gitignored (verified with `git check-ignore`). The scanner also rejects those names if ever staged. A grep of the working tree and all git history for each seed in the wallets file found 0 hits (counts only; see Verification).
2. Network fail-closed. F-01 to F-03. The kill-switch default in the policy engine is exact `=== "true"` (`packages/policy-engine/src/evaluate.ts:54`), missing or malformed blocks.
3. Input validation. Amounts: strings only, regex bounded to 12 integer and 6 fractional digits, compared with `decimal.js` (adapter) and `BigInt` drops (policy). Addresses: `isValidClassicAddress` in policy engine, adapter (issuer) and scripts (wallet file, treasury argument). Currency compared case-insensitively as hex, issuer exactly, as a pair. Prototype pollution: no recursive merge or `Object.assign` of untrusted data anywhere; `JSON.parse` then spread does not set `__proto__`; `redactValue` drops `__proto__` keys. ReDoS: every regex in the repo was reviewed; money, time and file-name patterns are fully bounded and anchored, ENV and PEM patterns were rewritten (F-07); the lint rule `security/detect-unsafe-regex` runs with `--max-warnings 0`, with inline suppressions, each carrying a reason, only on fully bounded patterns where the heuristic gives false positives (five `detect-unsafe-regex`, four `detect-non-literal-regexp` built from constant rule tables). Path traversal: all file paths derive from fixed `ROOT` constants; run ids are UUID-validated, `--to` is an enum, so no user value reaches a path. The ESLint rule `security/detect-non-literal-fs-filename` is disabled for that reason, recorded in `eslint.config.mjs`.
4. Money and logic safety. No floats in money paths after F-11 (display-only `Number` use removed). Integer overflow: XRP in drops as `BigInt`/string, amounts bounded to 12 digits. TOCTOU between policy check and signing: not applicable yet (no guard); required controls are PG-2 and PG-3. Idempotency: the adapter checks the persisted hash on the ledger before any submit and resubmits only the identical blob while `LastLedgerSequence` is ahead. Partial payment: `tfPartialPayment`, `SendMax`, `DeliverMin` rejected; only validated `tesSUCCESS` with matching `delivered_amount` counts as paid. Replay: Sequence and `LastLedgerSequence` bound each blob. Keyed queue: serialises per address and survives a failing task; in-process only (PG-6). Error paths: submit errors and lookup errors stay `pending`, never "paid"; a damaged M1 log now blocks instead of resetting the budget.
5. Supply chain. All versions exact (checked every `package.json`; no `^ ~ * latest`). Lockfile: 211 integrity entries, all `sha512`, no git or tarball URLs. Packages are well known (xrpl, decimal.js, zod, dotenv, tsx, vitest, typescript, ripple-address-codec, eslint family, typescript-eslint, eslint-plugin-security); no typosquat-looking names. New dependencies in this task: `eslint`, `@eslint/js`, `typescript-eslint`, `eslint-plugin-security` (dev only) and `vitest` for `contracts` (already in the tree).
6. Logging and error handling. One helper, used everywhere (F-06, F-18). Stacks are never printed; `includeStack` is opt-in and redacted.
7. Git hygiene. F-07, F-16.
8. Future gaps (M3 to M8). Listed as binding rules with IDs in `docs/secure-coding-standards.md` (authentication and sessions, authorisation and RLS, CSRF/CORS/headers, SQL injection, output encoding of `agent_reason`, SSRF, hosting secrets, audit tamper evidence, CI dependency scanning, constant-time token compare and rotation, agent tool allowlist and bounds), mapped to OWASP ASVS, Top 10 and LLM Top 10.
